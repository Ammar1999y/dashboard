# مراجعة تنفيذ طبقة HTTP — نسخة عربية مبسّطة

هذه نسخة عربية من [التقرير الأصلي](http-layer-implementation-review.md). تحافظ على الملاحظات الـ 17 وترتيبها وأولوياتها، وتشرح المشكلة وأثرها والإصلاح المقترح بلغة أبسط. الأدلة والأرقام ونتائج الاختبارات المذكورة هنا من التقرير الأصلي، وأرقام الأسطر تشير إلى النسخة التي راجعها ذلك التقرير.

طبقة HTTP هي الجزء الذي يستقبل طلبات التطبيق، ويتحقق من هوية المستخدم وصلاحياته وصحة المدخلات، ثم يعيد الرد. تراجع هذه الوثيقة مدى توافق التنفيذ الجديد مع السلوك المتوقع، ووثيقة API، والاختبارات.

## كيف تقرأ التقرير؟

| المصطلح                 | معناه هنا                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| عقد API                 | تعريف ما يقبله المسار من مدخلات، وما يعيده من بيانات وأخطاء.                                |
| `binding`               | ربط تعريف المسار بسياسة الوصول إليه والدالة التي تنفذ عمله.                                 |
| `schema`                | قواعد تحدد شكل البيانات والقيم المسموح بها.                                                 |
| OpenAPI                 | وثيقة تصف مسارات API ومدخلاتها وردودها، ويمكن للأدوات استخدامها للتحقق أو إنشاء عميل API.   |
| OTP                     | رمز تحقق مؤقت يُرسل إلى البريد أو الهاتف.                                                   |
| إعادة التحقق من الهوية  | تأكيد حديث لهوية المستخدم قبل عملية حساسة؛ وجود جلسة دخول وحده لا يكفي.                     |
| نافذة إعادة التحقق      | المدة التي يظل خلالها ذلك التأكيد الحديث صالحًا لتنفيذ العمليات الحساسة.                    |
| غلاف الرد               | الشكل العام لرد JSON، مثل الحقول `data` و`code`.                                            |
| اختبار تجريبي، أو probe | تجربة محددة استخدمها التقرير لإعادة إنتاج سلوك أو مشكلة.                                    |
| أصل الموقع، أو origin   | البروتوكول واسم المضيف والمنفذ معًا؛ اختلاف أي منها يعني أصلًا مختلفًا بالنسبة إلى المتصفح. |

الأولويات كما وردت في الأصل:

- **P2:** مشكلات مهمة في السلوك أو الحماية أو توافق الردود.
- **P3:** مشكلات أقل أولوية، تشمل اتساق السلوك والتوثيق والاختبارات وقابلية الصيانة.

ولفهم الأمثلة: `400` طلب مرفوض، و`401` يحتاج إلى تحقق من الهوية، و`403` غير مسموح، و`404` غير موجود، و`409` تعارض، و`413` حجم الطلب أكبر من المسموح، و`422` مدخلات غير صالحة، و`429` تجاوز حد المحاولات، و`500` خطأ داخلي.

## 1. [P2] ثلاث عمليات تحول تجاوز حد OTP من 429 إلى 500 خارج الإنتاج

**الفكرة ببساطة:** المستخدم يتجاوز حد المحاولات، فيجب أن يتلقى `429` مع سبب واضح ووقت انتظار. لكن تعريف بعض المسارات لا يذكر هذا الخطأ، فتستبدله طبقة HTTP بخطأ داخلي `500` خارج الإنتاج.

**المسارات المتأثرة:**

- إكمال إعادة تعيين كلمة المرور: `completePasswordReset`، في `packages/shared/src/api/auth.ts:96-104`.
- بدء تغيير البريد: `changeEmail`، في `packages/shared/src/api/users.ts:164-172`.
- بدء تغيير الهاتف: `changePhone`، في الملف نفسه، الأسطر `195-203`.

إكمال إعادة التعيين قد يبلغ حد التحقق من الرمز أو الحد اليومي. تغيير البريد والهاتف قد يبلغان حد إرسال الرموز. جميعها يمكن أن تعيد `429 otp_proof_throttle`، لكن تعريفاتها لا تعلن هذا الرمز.

**الأثر:** الدالة `declared()` في `apps/back-end/lib/http/run.ts:165-180` تستبدل الرد بخطأ `500`. يضيع رمز الخطأ، ورسالة الحظر، وترويسة `Retry-After` التي تخبر العميل متى يعيد المحاولة. قبل إعادة الكتابة، كان رد `429` وترويسة الانتظار يصلان في جميع البيئات.

هناك نقص آخر: `completePasswordReset` قد يعيد `404 codeNotSent` عند عدم وجود سجل رمز، لكنه لا يعلن `404` أيضًا.

**الدليل:** اختبارات `complete.probe.test.ts` و`codes.probe.test.ts` و`codes2.probe.test.ts` أعادت إنتاج ردود `500` عند بلوغ الحدود. مسار إرسال العامل الثاني، الذي يعلن الخطأ، أعاد `429` الصحيح. وأعاد اختبار مستقل إنتاج الحالات الثلاث.

**الإصلاح المقترح:**

- إضافة `429: { codes: [OTP_PROOF_THROTTLE_CODE] }` إلى تعريفات المسارات الثلاثة.
- إضافة `404: {}` إلى `completePasswordReset`.
- اختبار حالة تجاوز الحد لكل مسار، مع التحقق من الحالة ورمز الخطأ و`Retry-After` معًا، واختبار غياب سجل الرمز.

## 2. [P2] فحص توافق الأخطاء مع العقد غير مكتمل ويتصرف بشكل مختلف بين البيئات

**الفكرة ببساطة:** توجد دالة يفترض أن تكشف الردود التي لا يعلنها عقد المسار، لكنها تفحص جزءًا من الرد فقط، وتعاقب بعض المخالفات في التطوير دون الإنتاج، ولا تسجلها بالشكل المطلوب أثناء الاختبارات.

**أين؟** `apps/back-end/lib/http/run.ts:165-180`، في `declared()`.

**المشكلة الأولى: تفحص رمز الخطأ، لكنها لا تفحص حالة HTTP.**

إذا أعاد معالج الطلب `CustomError` بحالة غير موجودة في `refusalsOf(binding)`، قد يمر الرد دون تسجيل مخالفة. أمثلة وجدها التقرير:

| العملية                              | الرد غير المعلن                                                  |
| ------------------------------------ | ---------------------------------------------------------------- |
| إنشاء مستخدم، `POST /api/dash/users` | `404` عند فحص الدور القابل للإسناد؛ مشكلة سابقة.                 |
| تأكيد تغيير البريد                   | `404 codeNotSent`؛ مشكلة سابقة، بينما مسار الهاتف يعلنه.         |
| إنشاء صلاحية أو تعديلها              | `400` عند مخالفة قاعدة أسماء الأدوار ذات بادئة `custom-`.        |
| بدء تغيير البريد أو الهاتف           | `400` لكلمة مرور خاطئة أو لطلب استخدام جهة التواصل نفسها.        |
| تأكيد تغيير البريد أو الهاتف         | `400` لرمز خاطئ أو منتهي الصلاحية.                               |
| إنشاء مستخدم                         | `400` عند رفض كلمة المرور بواسطة فحص كلمات المرور المكشوفة HIBP. |
| تعديل مستخدم                         | `400` عند محاولة تعيين كلمة مرور لحساب دخول موحد SSO.            |
| 19 عملية لا تستقبل جسم طلب           | `413` بسبب فحص الحجم المعلن في الترويسة؛ مشكلة سابقة.            |

كما أن وثيقة API تصف `400` بأنه قد ينتج عن مخالفة قواعد العملية فقط عندما يكون `errors[400]` معلنًا. لذلك تصف بعض المسارات هذا الرد كخطأ في شكل المدخلات فقط، رغم وجود أسباب أخرى.

**المشكلة الثانية: التطوير والإنتاج يعيدان سلوكًا مختلفًا.**

الفحص يعمل بشرط `NODE_ENV !== 'production'`. لذلك قد تعيد الحالة نفسها `500` في التطوير و`429` الصحيح في الإنتاج. فحص عقد رد النجاح، عبر `responseCheckMode()`، يتبع سياسة مختلفة: يسجل فقط في التطوير، ويفرض الفحص ويسجل المخالفة أثناء تشغيل الاختبارات.

**المشكلة الثالثة: لا تُسجل مخالفة العقد لدى مشغّل الاختبارات.**

قد لا يفشل الاختبار إلا إذا كان يفحص حالة الرد تحديدًا؛ وجود رد `500` غير صحيح وحده لا يضمن اكتشاف المشكلة.

**الدليل:** تجارب `probes-media-perm/refusals.ts` و`probes-openapi/runtime-vs-doc.ts` و`probes-core/p9-codes.ts`، ومقارنة المستندات في `probes-users/cmp*.ts`.

**الإصلاح المقترح:**

- توحيد سياسة الفحص باستخدام `responseCheckMode()`: في وضع التسجيل، تُسجل المخالفة ويظل الرد كما هو؛ وفي وضع الفرض، تُسجل لدى مشغّل الاختبارات ويعاد `500`.
- فحص حالة HTTP أيضًا، وإعلان الحالات الناقصة في الجدول.
- إعلان `400: {}` عندما يمكن لقواعد العملية رفض الطلب بهذه الحالة.
- إما إعلان `413` لكل المسارات، أو عدم إجراء فحص الحجم المعلن للمسارات التي لا تستقبل جسم طلب.

## 3. [P2] وثيقة OpenAPI ترفض null في 10 حقول تسمح به فعليًا

**الفكرة ببساطة:** بعض الحقول تقبل قيمة من قائمة محددة أو `null`. بعد تحويل تعريفها إلى OpenAPI، تبقى `null` ضمن الأنواع المسموحة لكنها لا تضاف إلى قائمة القيم المسموحة، فيصبح التعريف متناقضًا.

مثال توضيحي على الشكل الخاطئ:

```json
{
  "type": ["string", "null"],
  "enum": ["a", "b"]
}
```

قائمة `enum` تُفحص بصورة مستقلة عن `type`، ولذلك يجب أن تتضمن `null` أيضًا.

**أين؟** استدعاء `toOpenAPISchema` في `apps/back-end/server/elysia/openapi.ts:32`. يحدد التقرير السبب في تحويل داخل إصدار `@elysia/openapi@2.0.0-beta.4`، ولا تصححه مرحلة `lib/http/openapi/finalize.ts`.

**الحقول المتأثرة:**

- `transition` في ردود قائمة الوسائط، وإنشاء ملف، وجلب ملف، ونشره وإلغاء نشره، ورفع ملف.
- `options[].contactKind` و`options[].channel` في رد `POST /api/auth/forgot-password/reset`.

**الأثر:** قد يرفض عميل يعتمد على الوثيقة ردًا صحيحًا من الخادم. وثيقة النسخة السابقة استخدمت `anyOf` الصحيح ولم تحتوِ هذه الحالات.

**الدليل:** تجربة `probes-openapi/ajv-null-enum.ts` رفضت `null` بسبب `enum`. فحص الوثيقة الجديدة وجد 10 مواضع مقابل صفر في السابقة. الاختبارات الحالية تتحقق من صلاحية الوثيقة نفسها، ولا تثبت قبولها للردود الحقيقية.

**الإصلاح المقترح:** عندما يتضمن `type` النوع `null`، تُضاف `null` إلى `enum`. وإذا كان التعريف يستخدم `const: x`، يُحوّل إلى `enum: [x, null]`. يُضاف اختبار يمشي على كامل الوثيقة لاكتشاف هذا التعارض، وتُبلّغ المكتبة بالمشكلة.

## 4. [P2] اختبار إعادة التحقق من الهوية يؤكد الإعداد نفسه بدل التأكد من الحماية

**الفكرة ببساطة:** الاختبار يقرأ إعداد `reauth`، ثم يبني النتيجة المتوقعة من الإعداد نفسه. إذا عُطلت الحماية بالخطأ، قد يظل الاختبار ناجحًا.

**أين؟** `apps/back-end/tests/unit/route-auth-flags.test.ts:65-73` و`apps/back-end/lib/http/admit.ts:77-81`.

سابقًا كان الاختبار يقارن الإعداد بما يصل إليه كود المعالج فعلًا من فحص نافذة إعادة التحقق. الآن يضيف بوابة `window` عندما تقول `gateAsksReauth(binding)` إن الإعداد يطلبها؛ والدالة نفسها تعتمد على `policy.reauth`. هكذا تصبح المقارنة دائرية.

**المسارات الستة المتأثرة:**

- `POST /api/dash/permissions`.
- `PUT /api/dash/permissions/:id`.
- `DELETE /api/dash/permissions/:id`.
- `POST /api/dash/users`.
- `DELETE /api/dash/users/:id`.
- `POST /api/dash/users/:id/two-factor/reset`.

**الأثر:** خمسة من هذه المسارات لا تملك اختبارًا فعليًا مستقلًا يثبت رفض العملية عند غياب إعادة التحقق. تغيير `reauth` إلى `false` قد يزيل الحماية عن عملية إدارية حساسة دون فشل الاختبارات. إنشاء المستخدم وحده لديه اختبار فعلي لرد `401 REAUTH_REQUIRED`.

**الإصلاح المقترح:** تثبيت قائمة مستقلة بالمسارات التي يجب أن تتطلب إعادة التحقق في `bindings.test.ts`، ثم اختبار كل مسار بجلسة لا تملك نافذة صالحة. يجب أن يكون الرد `401 REAUTH_REQUIRED`، وأن يرفض الطلب قبل قراءة جسمه.

## 5. [P3] رفض تكرار معاملات الرابط يحدث مبكرًا ويشمل معاملات غير معرّفة

**الفكرة ببساطة:** التحقق من تكرار معاملات الاستعلام، مثل `?deep=1&deep=1`، يحدث قبل بعض الفحوص التي يفترض أن تسبقه. كما أنه يرفض تكرار معامل لا يستخدمه المسار أصلًا.

**أين؟** `apps/back-end/lib/http/admit.ts:148-151`.

**مثال فحص التخزين، GET /api/health/storage:**

هذا المسار يفحص `x-maintenance-token` داخل المعالج قبل أي رد. لكن فحص التكرار الجديد يسبق المعالج:

| الطلب                              | السلوك السابق                     | السلوك الجديد                               |
| ---------------------------------- | --------------------------------- | ------------------------------------------- |
| بلا رمز صيانة، مع `?deep=1&deep=1` | `401` بالصيغة الخاصة بالمسار      | `422` بغلاف الرد العام                      |
| برمز صيانة صحيح، مع `?a=1&a=2`     | `200`؛ المعامل غير معروف ويُتجاهل | `422` دون حقل `status` الذي يقرأه فحص النشر |

**مثال حذف مجلد:** طلب `…/folders/not-an-id?recursive=true&recursive=true` يعيد الآن `422 MSG_INVALID_INPUT` بدل `404 FOLDER_NOT_FOUND` الخاص بالمعرّف غير الصالح. بذلك تغير ترتيب الأخطاء.

**الدليل:** `probes-media-perm/perm.probe.test.ts` و`probes-media/order.test.ts`. لا يوجد اختبار يغطي حالة فحص التخزين المذكورة ضمن التغييرات المتعمدة في الخطة.

**الإصلاح المقترح:** رفض تكرار المعاملات التي يعرّفها مخطط الاستعلام فقط. يوضع الفحص عند مرحلة التحقق من الاستعلام، بعد معاملات المسار، مع الحفاظ على أسبقية فحص رمز الصيانة. تُضاف اختبارات لحالة التخزين وللمعرّف غير الصالح مع معامل مكرر.

## 6. [P3] جميع ردود الأخطاء تسمح الآن ببيانات تخص الوسائط

**الفكرة ببساطة:** معظم الأخطاء يجب أن تكون `data: null`. بعض أخطاء الوسائط تحتاج إلى معرّفات ملفات أو مجلدات. لكن التعريف الجديد يسمح بهذه المعرّفات في جميع أخطاء جميع المسارات.

**أين؟**

- `packages/shared/src/response-contract.ts:171-176`.
- `apps/back-end/server/elysia/register.ts:23,32-34`.
- `apps/back-end/lib/http/openapi/merge-better-auth.ts:61,537`.

**الأثر:** 390 رد خطأ موزعة على 50 عملية تعلن قبول `{ fileIds?, folderIds? } | null`، حتى في أخطاء المستخدمين والمصادقة مثل `401` و`403` و`429` و`503`. هذا يضعف دقة العقد.

يتكرر التعريف داخل الوثيقة 390 مرة، ويشكل 61% من حجم JSON بصيغته المضغوطة، بينما استخدمت النسخة السابقة مرجعًا مشتركًا `$ref`. كما أصبح الاختبار الذي يربط كل حالة خطأ بالغلاف المناسب لها أضعف.

**الإصلاح المقترح:** استخدام `data: null` افتراضيًا، والسماح ببيانات الوسائط فقط عند إعلان رمز خطأ يحتاج إلى تلك المعرّفات في الحالة المعنية. يُنشر الغلافان كتعريفين مشتركين مع `$ref`، ويُعاد الاختبار الدقيق لكل حالة.

## 7. [P3] التحقق من رد HEAD يختلف عن GET

**الفكرة ببساطة:** يفترض أن يعيد `HEAD` الحالة والترويسات المتوافقة مع `GET` دون جسم الرد. لكن لكل منهما طريقة تحقق مختلفة، وقد ينتجان حالتين أو ترويسات مختلفتين.

**أين؟** `apps/back-end/server/elysia/register.ts:84-109`، مع `respond.ts:111-125` و`errors.ts:43-49`.

يتحقق Elysia من رد `GET` وفق مخططات جميع الحالات. أما `HEAD` فيعيد `Response` مباشرة ويجري تحققًا منفصلًا عبر `success.safeParse` لحالة النجاح فقط.

**الاختلافات التي أثبتها التقرير:**

- الحقول الزائدة في جسم خطأ بصيغة المسار تُحذف مع `GET`، وتبقى ضمن حساب طول رد `HEAD`. مثال: `Content-Length` يساوي 25 في الأول و52 في الثاني.
- جسم خطأ غير مطابق للمخطط يؤدي إلى `500` مع `GET`، لكنه قد يمر بحالته الأصلية، مثل `401`، مع `HEAD`.
- عند فشل تحقق رد النجاح، يحتفظ `GET` بترويسات المعالج على رد `500`، بينما لا يحتفظ بها `HEAD`.

**الأثر:** خلل في توافق `HEAD` و`GET`. كذلك قد يصبح الاحتفاظ بترويسات النجاح على خطأ `500` مشكلة تخزين مؤقت مستقبلًا إذا أضاف معالج ترويسة مثل `Cache-Control: public`.

**الدليل وحدوده:** `probes-core/p8-head-raw.ts`، وتجربة مستقلة عبر `app.handle` وخادم Bun فعلي. المشكلة كامنة حاليًا: ردود الأخطاء الخاصة بفحص التخزين تطابق المخطط، ولا توجد معالجات تعيد ترويسات بعد.

**الإصلاح المقترح:** توحيد التحقق داخل `runBinding` باستخدام المخططات المترجمة نفسها لجميع الحالات المعادة كقيم، ثم إعادة `Response` مباشرة لجميع الردود. عند فشل التحقق، تُحذف ترويسات المعالج من رد `500`. يزيل ذلك مسار التحقق المكرر وكتابة سياسة الرد مرتين، ويتطلب تعديل قرار الخطة الذي يعتمد على تحقق Elysia الأصلي.

## 8. [P3] صفحة /openapi في التطوير تتجاوز نظام تسجيل المسارات

**الفكرة ببساطة:** صفحة التوثيق تُسجل مباشرة باستخدام `app.get`، فتفقد السلوك الموحد الذي تحصل عليه المسارات المسجلة عبر `bind()`.

**أين؟** `apps/back-end/server/elysia/openapi.ts:63-84` و`apps/back-end/app.ts:210-213`.

**النتيجة التي وجدها الاختبار:**

| الطلب              | الرد الحالي                             |
| ------------------ | --------------------------------------- |
| `GET /openapi`     | `200`                                   |
| `HEAD /openapi`    | `404`                                   |
| `OPTIONS /openapi` | `404`                                   |
| `GET /openapi/`    | `404`، دون تحويل `308`                  |
| `POST /openapi`    | `404`، دون `Allow` أو سلوك `405` الموحد |

كما لا تمر الصفحة بحد الطلبات لكل عنوان IP قبل المصادقة. يذكر التقرير أن هذا يخالف قاعدة تسجيل المسارات في `apps/back-end/CLAUDE.md`.

سكريبت Scalar المحمل من CDN لا يملك خاصية `integrity`. سياسة CSP تقيد مساره، لكنها لا تتحقق من محتوى الملف؛ استبداله قد يجعل كودًا مختلفًا يعمل على أصل API مع جلسة المطور.

**الدليل:** `probes-core/p7-refpage.test.ts`. الصفحة متاحة في التطوير فقط، لذا أثر المشكلة منخفض.

**الإصلاح المقترح:** إدخال شكل مسار الصفحة في `createRouting` وإضافة `HEAD` بالآلية المشتركة. أو توثيقها كاستثناء مقصود في تعليمات المشروع، لأن صفحة HTML لا تلائم عقد JSON المعتاد. وتُضاف حماية SRI للتحقق من محتوى سكريبت Scalar.

## 9. [P3] نصوص توثيق OpenAPI تصل إلى حزمة المتصفح

**الفكرة ببساطة:** ملفات التحقق المشتركة يستخدمها الخادم والواجهة. وضع نصوص توثيق داخلها يجعل المتصفح يحصل على نصوص يفترض أن يحتاج إليها الخادم فقط.

**أين؟** أُضيف نص عن تعطيل إدخال الهاتف في `packages/shared/src/validation/auth.ts:176-177`، داخل `.meta({ allOf })`. المخططان `createUserSchema` و`adminUpdateUserBodySchema` اللذان يستخدمانه تستوردهما الواجهة.

كما بقيت نصوص مشابهة في ملفات عدّلها التغيير: `validation/rules.ts` و`media.ts` و`permissions.ts` و`auth.ts` و`two-factor.ts`.

**الأثر:** يخالف ذلك فصل التوثيق عن البيانات المشتركة. بحسب التقرير، تنص تعليمات المشروع على وضع أوصاف الحقول في `*.docs.ts` وتحميلها من الخادم فقط، وعلى إكمال التزام الملفات التي يجري تعديلها بهذه القاعدة.

قاعدة منع استيراد ملفات التوثيق لا تكفي: يمكن وضع الوصف مباشرة في `.meta({ description })` أو `.describe()`، فلا يكون هناك استيراد ممنوع أصلًا.

**الدليل:** بناء مصغّر للمتصفح باستخدام `Bun.build` على `validation/auth.ts` احتوى النص الجديد.

**الإصلاح المقترح:** نقل النصوص إلى ملفات `*.docs.ts`، والسماح لتعريف التوثيق باستهداف مخطط مشترك مثل `idSchema`. تُضاف قاعدة lint تمنع أوصاف `.meta()` واستدعاءات `.describe()` خارج ملفات التوثيق.

## 10. [P3] وثيقة API تحتوي أوصافًا خاطئة وتفتقد معلومات كانت موجودة

**الفكرة ببساطة:** بعض الأوصاف لا تعكس السبب الحقيقي للرد، وبعض الحقول والأمثلة فقدت توثيقها. وقد يرفض العميل طلبًا صحيحًا إذا اعتمد على الوثيقة وحدها.

**أبرز الحالات:**

| الموضع                                           | المشكلة                                                                                                                                                          |
| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/auth/forgot-password/reset`، رد `403` | الوصف يقول إن المتصل يفتقد صلاحية، بينما السبب المعلن هو `recoveryBlockedByTwoFactor`. هذا مسار عام، وكلمة grant قد تختلط بتصريح الاسترداد الذي يصدره الرد نفسه. |
| `POST /api/dash/users`                           | اختفى وصف حقل `permissions` لأن نسخة المخطط المستخدمة لا يصل إليها ملف التوثيق.                                                                                  |
| `POST /api/upload/file`، رد `201`                | اختفى وصف `data[].url` للسبب نفسه.                                                                                                                               |
| قوائم جداول البيانات الثلاث وفحص التخزين         | اختفت أمثلة `sort` و`deep`.                                                                                                                                      |
| `GET /api/dash/users/{id}`                       | اختفت قاعدة `dependentRequired` التي تصف اعتماد وجود حقول على حقول أخرى. يمكن إضافتها في المعالجة النهائية حتى لو لم تدعمها `.meta()`.                           |
| توثيق الصلاحيات                                  | يقول إن الإجراء غير المتاح تكون قيمته دائمًا `false`، بينما مفتاحه يغيب من الرد.                                                                                 |
| توثيق OTP                                        | يذكر «ست خانات» كنص ثابت بدل استخدام `OTP_CODE_LENGTH`.                                                                                                          |

هناك نقص سابق أيضًا في `GET /api/dash/media`: الخادم يقبل `?folder=` للإشارة إلى الجذر، لكن الوثيقة تسمح فقط بقيمة UUID. لذلك قد يرفض عميل يتحقق من الطلب وفق الوثيقة قيمة يقبلها الخادم.

**أين؟** `apps/back-end/lib/http/refusals.ts:124-128`، و`modules/auth/recovery.ts:194-198`، وملفات التوثيق والمخططات داخل `packages/shared/src/`، ومنها `validation/media.ts:237-244`.

**الدليل وحدوده:** تجربة `probes-media-perm/detail.probe.test.ts` أثبتت غياب مفاتيح الإجراءات غير المتاحة، وفحص الوثيقة الجديدة أثبت قيد `folder`. أما الادعاء المشابه عن `cursor` للجلسات فليس مشكلة بحسب التقرير: قيمته يصدرها الخادم، وتوثيق صورته القياسية مقصود.

**الإصلاح المقترح:**

- تخصيص وصف رد `403` لمسار الاسترداد، عبر `detail.responses[403]` أو وصف خاص بكل حالة داخل `errors`.
- توثيق `folder` كقيمة UUID أو سلسلة فارغة، وإضافة اختبار يقارن قبول المخطط بما تنشره الوثيقة.
- استعادة الأوصاف والأمثلة والقواعد المفقودة باستخدام ملفات التوثيق أو بيانات العمليات.
- تصحيح وصف الصلاحيات، وتوليد طول OTP من `OTP_CODE_LENGTH`.

## 11. [P3] تعذر تحويل مخطط الطلب قد ينتج تعريفًا مفتوحًا دون تنبيه

**الفكرة ببساطة:** إذا عجز Zod عن تحويل أحد حقول الطلب إلى JSON Schema، تسمح الإعدادات الحالية بنشره كـ `{}`. هذا تعريف بلا قيود، وقد يخفي نقصًا في الوثيقة.

**أين؟** `apps/back-end/lib/http/openapi/finalize.ts:98-101`، و`merge-better-auth.ts:381` لطلبات Better Auth.

إعداد الطلبات هو `unrepresentable: 'any'`، بينما الردود تستخدم `'throw'` الذي يوقف التحويل ويكشف المشكلة بدل تجاوزها.

**الدليل:** تجربة `probes-openapi/unrep.ts` حولت جميع مخططات أجسام الطلبات، بما فيها `publishedBody` و`BETTER_AUTH_BODIES`، باستخدام `'throw'` ولم يفشل أي منها. إذن لا توجد حالة حالية تحتاج إلى التساهل.

**الإصلاح المقترح:** استخدام `unrepresentable: 'throw'` للطلبات أيضًا.

## 12. [P3] بعض أدوات منع المخالفات يمكن تجاوزها

**الفكرة ببساطة:** إعادة الكتابة تعتمد على أدوات لفحص تسجيل المسارات وحدود الاستيراد وصحة الإعدادات. لكن هذه الأدوات لا تغطي كل الأشكال التي يمكن أن يكتب بها المطور الكود.

**أولًا: أداة اكتشاف المسارات لا تتعرف على جميع صيغ تعريف binding.**

في `apps/back-end/scripts/find-unused-files.ts:171` تتعرف `EXPORTED_BINDING` فقط على الشكل `export const X = bind(`. لا تكشف بعض المسارات غير المسجلة إذا كُتبت مثل:

```ts
export const X: T = bind(...)
const X = bind(...); export { X }
bind<T>(...)
(bind(...))
```

هذه أمثلة على صيغ الكتابة، وليست كودًا جاهزًا للتشغيل. التجربة `probes-shared-tooling-tests-tooling/fu-tree/` أثبتت مرور الأشكال الأربعة.

**ثانيًا: قواعد منع الاستيراد لا تغطي الاستيراد الديناميكي.**

يمكن كتابة `import('elysia')` أو استيراد ملف `*.docs` ديناميكيًا دون مخالفة lint، رغم أن `docs/framework-migration.md` يقول إن ESLint يمنعهما. لا يوجد اختبار لقاعدة المنع في هاتين الحالتين.

**ثالثًا: يقبل binding إعداد رفض لجزء غير موجود في الطلب.**

يمكن وضع `refusals.body` على مسار بلا جسم طلب، أو `refusals.params` على مسار بلا معاملات مسار. يقبل الكود ذلك ويصبح الإعداد بلا أثر. فحص `assertAgrees` في `lib/http/binding.ts:325-364` لا يرفضه، بينما كان هناك اختبار يرفضه قبل إعادة الكتابة.

**رابعًا: اختبار الصلاحيات يستنتج الحماية من التوثيق.**

في `tests/integration/mutating-route-authorization.test.ts:40`، يعتمد إدراج المسار في اختبار `403` على `entry.errors?.[403]`. إذا نسي المطور إعلان الرد، يخرج المسار من الاختبار، رغم أن سياسة الوصول هي المصدر الذي ينبغي فحصه.

**الإصلاح المقترح:**

- فحص التسجيل أثناء التشغيل: كل قيمة `bind()` مصدّرة من `modules/*/*.ts` يجب أن تكون ضمن `BINDINGS`.
- إضافة قاعدة `no-restricted-syntax` للاستيراد الديناميكي `ImportExpression` من `elysia` و`@elysia/*` و`*.docs`، مع استثناء محمّل التوثيق `lib/http/openapi/docs.ts`، واختبار القاعدة.
- جعل `assertAgrees` يرفض إعدادات الرفض التي لا يقابلها جزء فعلي من الطلب.
- جعل اختبار الصلاحيات يقرأ نوع المصادقة من السياسة بدل قائمة الأخطاء الموثقة.

## 14. [P3] بعض الاختبارات تنجح دون أن تثبت السلوك المطلوب

**الفكرة ببساطة:** الاختبارات موجودة، لكن بعضها لا يمر بالحالات المهمة، أو يتساهل مع حقول زائدة، أو يبني توقعاته من المصدر نفسه الذي قد يحتوي الخطأ. لذلك نجاح المجموعة لا يكفي لإثبات صحة التنفيذ.

**اختبار المخططات المترجمة لا يجرب مدخلات صحيحة لكثير منها.**

في `tests/unit/zod-compile.test.ts:182-203`، لا يحصل 81 مخططًا من أصل 207 على أي مدخل يقبله التحليل العادي. تشمل هذه المجموعة جميع أجسام الطلبات وجميع مخططات معاملات `:id`.

إذا كان التنفيذ المترجم يرفض مدخلًا صحيحًا أو يحوله بشكل خاطئ، فلن تكشفه تلك الحالات. شرط `inputs.length > 3` لا يمكن أن يفشل كما كُتب، وغلاف الخطأ المترجم ومخططات الأخطاء ذات الصيغة الخاصة غير مدرجة في المقارنة.

**تغييرات مقصودة في السلوك لا تملك اختبارات، رغم أن الخطة تطلب ذلك:**

- فحص التخزين مع معامل مكرر أو غير معروف.
- `POST /api/dash/media/files` مع معامل غير معروف أو `folder` مكرر.
- `GET /api/dash/users/:id/sessions` لمستخدم لا يمكن الوصول إليه: أسبقية `422` على `404`.
- `PUT /api/dash/media/folders/:id`: فحص الجسم قبل `404` لمعرّف غير صالح.
- `PUT /api/dash/users/me` دون نافذة إعادة تحقق صالحة؛ الاختبارات الحالية لمسارات `/me` تدخل بنافذة مفتوحة.

**دوال مساعدة تخفي الحقول الزائدة في الرد.**

`expectData` و`expectError` في `tests/helpers/expect-body.ts:41-57` تحللان الرد بمخططات غير صارمة وتعيدان البيانات بعد التحليل. قد تُحذف الحقول الزائدة أثناء التحليل، فلا يرى الاختبار تسريب حقل غير متوقع. كما أن عدة اختبارات تفحص حالة HTTP فقط.

**اختبارات تمر على قائمة فارغة دون فشل.**

اختبارات الجلسة والترويسات الأمنية والصلاحيات وcaptcha في `binding-gate.test.ts` تستخدم قوائم مُرشّحة دون تأكيد حجمها. أثبتت التجربة أن `describe.each` على قائمة فارغة ينجح في إصدار Bun الذي فحصه التقرير، أي يمكن أن ينجح الاختبار دون فحص أي مسار.

**تغطية HEAD محدودة.**

`head-method.test.ts` يغطي مسارين فقط. الجزء الذي يستخدم اتصالًا فعليًا يقارن `Content-Length` فقط، ولا يختبر `HEAD` مع ردود الأخطاء.

**فحوص أصبحت أضعف أو اختفت:**

- استُبدلت مقارنة كاملة `toEqual` بمقارنة جزئية `toMatchObject` في أحد اختبارات عقد OpenAPI.
- اختفى فحص قائمة المفاتيح الدقيقة لـ `SPENT_INPUT_REMEDIES`، واستُبدل بفحص نصوص لكل مسار.
- اختبار `checkSuccess` يفحص إرجاع `false`، دون اختبار مباشر لتحويل الفشل إلى رد `500` في `run.ts`.
- لا يوجد بديل لاختباري توليد الوثيقة مرة واحدة والاحتفاظ بنتيجة فشل توليدها في `lib/http/openapi/serve.ts`.
- استُبدلت حالات العقود الحقيقية في اختبار الأنواع بمخططات اصطناعية.
- ملف `_route-feature-gates-child.ts` يبني الرد المتوقع بنفسه، فلا يكشف اختلاف التنفيذ عن العقد.

**ثغرات أخرى في التغطية:**

- حماية captcha في مسارات `/me` من نوع `SELF_SERVICE` لا تُقارن بمرجع مستقل؛ الإعداد والبوابة والتوثيق والاختبار مشتقة من `policy.captcha` نفسه.
- فرع في `user-bindings.test.ts:126-139` لا يعمل مع الإعداد المرفق `REQUIRE_ROLE_FOR_LOGIN=true` بسبب خروج مبكر.
- لا تُولّد وثيقة OpenAPI في اختبارات التهيئات الست للمصادقة الثنائية، رغم أن جزء Better Auth يعتمد على هذه الإعدادات.

**الدليل:** أبرز المراجع `probes-shared-tooling-tests-unit/zc-probe.ts` وتجربة القائمة الفارغة داخل `probes-shared-tooling-tests-integ/empty/`، إضافة إلى مقارنة الاختبارات بالنسخة السابقة.

**الإصلاح المقترح:**

- إعطاء كل مخطط مترجم مثالًا صحيحًا مكتوبًا يدويًا، وإضافة اختبارات التغييرات المتعمدة.
- مقارنة جسم الرد الأصلي مع `parsed.data` باستخدام `toEqual` في `expectData`، واستخدام نسخة `.strict()` في `expectError`.
- التأكد من أن قوائم المسارات المختبرة تحتوي العدد المتوقع، حتى لا ينجح الاختبار على قائمة فارغة.
- توسيع اختبار `HEAD` ليشمل الأخطاء و`/openapi.json`.
- استعادة الفحوص الدقيقة والحالات التي اختفت.
- توليد الوثيقة والتحقق منها داخل `tests/matrix/two-factor-configuration.test.ts`.

## 15. [P3] أجزاء من الكود والتعليقات تعطي القارئ صورة غير صحيحة

**الفكرة ببساطة:** توجد قيم لا تُستخدم، وفحوص لا يمكن الوصول إلى أثرها، وتعليقات تصف سلوكًا قديمًا. هذا يصعّب فهم موضع الحماية الحقيقي.

**قيمة actor محسوبة دون استخدام.**

`server/elysia/gate.ts:50-52` ينتج `actor` عبر `derive`، لكن المعالج يأخذ المستخدم من `actorOf(request)` في `lib/http/run.ts:42`. التعليق يوحي بأن `derive` يسلّم القيمة للمعالج، وهو ما لا يحدث.

الإصلاح: حذف `derive`، أو تمرير `context.actor` إلى `runBinding` وإزالة القراءة الثانية.

**فحوص دور لا تضيف حماية.**

توجد فحوص في `modules/users/self.ts:19-21` و`item.ts:53-56` و`sessions.ts:49-54`. لكن `Grants.roleId` يكون موجودًا دائمًا عند بلوغها؛ الجهتان اللتان تنتجان الصلاحيات ترفضان الطلب بـ `403` قبل ذلك إذا لم يكن متاحًا.

الإصلاح: حذف الفحوص والتعليقات التي تصورها كحماية فعلية. وبما أن `self.ts` له مستدعٍ واحد، يمكن دمجه في `me.ts`.

**تعليقات وتوثيق يحتاجان إلى تصحيح:**

- `error-codes.ts` و`response-contract.docs.ts` يقولان إن `otp_proof_throttle` لا يصل إلى مسار عام، بينما يمكن لمساري إرسال العامل الثاني وإكمال الاسترداد إعادته.
- تعريف `OTP_NEEDS_CONTACT_KIND` في `validation/two-factor.ts` فصل تعليق JSDoc عن المخطط الذي يصفه.
- بعض التعليقات في `modules/media/upload.ts` و`api/media.ts` تحيل إلى تنفيذ سابق أو رموز خطة مثل `D22` دون شرح يمكن للقارئ استخدامه.
- تعليق `lint-security-gate.test.ts` يصف ما يُشغّل بصورة غير دقيقة ويذكر قياسًا ثابتًا.
- مقدمة `openapi-document.test.ts` تقول إن الوثيقة لم تُنشر بعد، وهناك فحص يتجاوز المسار المفقود دون ضمان وجوده.
- `tests/helpers/session.ts` يقول إن مسار التطوير يعيد `403` في وضع الاختبار؛ الصحيح أنه غير مسجل ويعيد `404`.
- `apps/back-end/reports/test-strategy.md` لا يزال يصف ملفات وآليات قديمة، مثل `routes.ts` و`route-manifest.ts` و`app/api/**/handler.ts`.
- مهمة lefthook في `lefthook.yml:139` لا تزال باسم `routes`.

**الإصلاح المقترح:** تحديث التعليقات والمراجع لتصف التنفيذ الحالي، ونقل التعليقات إلى التعريفات الصحيحة، وحذف الكود غير المستخدم والفحوص التي لا تضيف أثرًا.

## 16. [P3] إعادة الكتابة أضافت تكرارًا ونقلت إعدادات خادم إلى ملفات مشتركة

**الفكرة ببساطة:** تكرار التعريف نفسه في عدة مواضع يجعل تعديله عرضة للنسيان. وبعض القيم أصبحت تصل إلى المتصفح فقط لاستخدامها في نصوص التوثيق.

**معاملات جداول البيانات معرفة ثلاث مرات.**

توجد المفاتيح في:

## 17. [P3] مشكلتان سابقتان بقيتا بعد نقل الكود

**الفكرة ببساطة:** إعادة الكتابة لم تنشئ المشكلتين التاليتين، لكنها نقلتهما إلى التنفيذ الجديد دون إصلاح.

**أولًا: التسجيل التطويري ببريد مكرر يعيد 500 بدل 409.**

في `POST /api/dev/sign-up`، ينشئ `modules/dev/sign-up.ts:36-44` الدور المرتبط بالبريد قبل إنشاء المستخدم. عند التسجيل بالبريد نفسه مرة ثانية، يصطدم بقيد اسم الدور `ux_roles_role_name`.

لا يحوّل `handleUserUniqueViolation` هذا التعارض إلى خطأ معروف، فيكون الرد `500`، رغم أن عقد المسار في `packages/shared/src/api/dev.ts:12` يعلن `409`.

الدليل: حالة `dev-dup` في `probes-media-perm/perm.probe.test.ts`.

الإصلاح المقترح: تحويل مخالفة هذا القيد في `mapError` إلى الرد المناسب، أو تسمية الدور بحسب معرّف المستخدم. يُضاف اختبار تسجيل بالبريد نفسه مرتين.

**ثانيًا: بعض الردود المبكرة تفتقد ترويسات CORS.**

رد `413` لفحص حجم الطلب في `app.ts:146-151`، ورد `404` للمضيف غير القابل للتوجيه في `app.ts:135-136`، يصدران قبل تشغيل إضافة CORS.
