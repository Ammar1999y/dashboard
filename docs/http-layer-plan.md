## 1. Owner priorities and decisions

### 1.1 Priorities (2026-10-09)

- **P1.** Write code framework-independent when there is a valid reason: performance, security or control. Not with needless complexity. Zod was chosen because it shares schemas and validation between the back end and the front end.
- **P2.** Use Elysia features that improve code quality or capability, even if a later move to Hono gets harder.
- **P3.** Keep Elysia-specific code in as few files as possible (wrappers, helpers, dedicated functions), so replacing Elysia touches few files.
- **P4.** Never restrict the design for Hono compatibility at the cost of functionality, quality or maintainability.

**Consequences, applied throughout:**

- No requirement that behaviour be "the same on both frameworks". No constraint exists only because of Hono.
- `server/elysia/` stays, only as the place where Elysia-specific code lives (P3).
- No Hono code in the repository (D26). Hono notes stay only where they help a future port, marked **non-binding**.

### 1.2 Standing decisions (2026-10-08, still in force)

1. **Frameworks.** Elysia 2. Next.js will not serve the API again. If it ever hosts it, it does so through one catch-all route exporting `app.fetch`.
2. **Zod is the only schema language,** in both apps. No TypeBox `t`.
3. **Native validation** through Standard Schema, and **native OpenAPI**.
4. **Nothing stays as-is just because it exists.** Every custom piece and every past rejection is weighed on merit (§8).
5. **Think through consequences:** CSP, Better Auth's client, test churn, boot time.
6. **Elysia 2 now,** so nothing is migrated twice.
7. **The Next-shaped layout goes** (`app/api/**/handler.ts` with `GET`/`POST` exports).
8. **Routes are bindings declared as data,** per domain module.
9. **The 2026-10-06 "no typed route-key client" decision is withdrawn.**

### 1.3 Decisions on the review (2026-10-09)

- All findings F1–F45 accepted as written, except:

The differential (A11) covered only our schemas. The gain on auth endpoints is negligible, and a compiler bug that accepts invalid input there would bypass Better Auth's validation unseen.
  - **F23:** `type: "about:blank"` on every problem; `code` is what clients branch on.
  - **F17:** add `PUT /api/dash/users/me`.
- **F21:** refinements pure, synchronous, cheap; the CI guard of D21.
- **Field descriptions:** option (c), D19.
- **Document rules:** in the shared schemas, D20.
- **A13's results** are adopted into D9.
- **Elysia `2.0.0-beta.27`,** exact pins; X2 dropped; X1 development only.
- **Phases** as in §12. Phase 0 is done.

## 2. Architecture: two layers

```
┌────────────────────────────────────────────────────────────────────────┐
│ CORE: framework-free                                                   │
│   packages/shared/src/api/*      endpoint contract (zod); typed client │
│                                  (Phase 4)                             │
│   packages/shared/src/**/*.docs.ts   field descriptions (D19)          │
│   modules/<domain>/*             bindings + handlers                   │
│   lib/http/*                     admit(), body reader, query check,    │
│                                  body builders, error mapping,         │
│                                  cookies, headers, route lookup,       │
│                                  after-response queue, document        │
│                                  finalizer, Better Auth merge          │
├────────────────────────────────────────────────────────────────────────┤
│ ELYSIA: every line that imports elysia or @elysia/*                    │
│   server/elysia/*.ts             about 7 files (§3)                    │
└────────────────────────────────────────────────────────────────────────┘
```

**Rules.**

- **Core never imports `elysia` or `@elysia/*`.** A lint rule enforces it on `modules/`, `lib/` and `packages/shared` (R13), for static and dynamic imports alike; a non-literal `import()` is refused (2026-10-14, #12).
- **Handlers are framework-free.** They receive `{ params, query, body, actor, meta }` and return `{ status?, message, data, meta?, headers?, cookies? }`, typed by `bind()` from the contract entry.
- **`server/elysia/*` holds wiring, not policy.** Logic that does not need Elysia lives in core, for control and testability (P1), not for Hono. Example: the document finalizer works on a plain object, so it is core (F41).
- **Elysia features are welcome (P2)** when they improve the code. Their calls live in `server/elysia/*` (P3).

**The behaviour suite** proves each phase and each Elysia bump:

- the existing integration, process and matrix tests, unchanged (D17);
- `bun run smoke`;
- the Elysia cases of §9.10.

## 4. How it works today, and what is wrong

**The pipeline.**

- `app.ts` is the only Elysia importer (1.4.30). It runs `onRequest`, CORS, routes, `mapResponse`, `onAfterResponse` and `onError`.
- 49 `routes.ts` rows are registered in a loop with `.route(...)` and `parse: 'none'`, through `toElysiaHandler` (`lib/http/adapters/elysia.ts`).
- 48 handlers in 33 files. Each calls its own auth, rate limit, captcha, `requireId` and `readJsonBody`.
- The contracts:
  - `REQUEST_BODIES` (28) and `RESPONSE_DATA` (47) in `packages/shared`;
  - `lib/http/openapi/`, **3,494 lines** (812 of them the Better Auth merge), building the document from about 13 route-keyed tables;
  - 87 front-end calls in 26 files, each a path string plus a hand-picked schema;
  - 71 MSW mocks in 14 files;
  - about 60 integration test files on `app.handle`; 48 assert `success` (134 times).

**Defects.**

1. One route's key is written 5–7 times, and the compiler links none of them.
2. The parsed schema is not tied to the published one. Query params are parsed by hand in five ways.
3. Extra response fields compile and ship in production.
4. The table only describes policies. An AST test and substring tests keep it in sync with the handlers.
5. Competing patterns: captcha refusal by `return` vs `throw`; fail-open read limiters; the body read before the id; the upload rate limit inside a library; a double session lookup; the unused `maxJsonBodyBytes`.
6. Media error data sits inside the generic error envelope.
7. Published prose hard-codes constant values.
8. Front end: nothing ties the href to the schema or body; 20 bodies typed by hand; `/api/dash/settings` exists only in the mocks; six Better Auth paths have no contract entry; no CSP is sent (`apps/front-end/next.config.js`: `headers = true ? [] : …`).
9. One new endpoint touches at least 8 files.

## 6. End-to-end types (D1)

### 6.1 The options

- **A. Eden (or `hc`) at the call sites.** Chained framework routes; the front end calls `api.api.dash.permissions({ id }).put(body)`.
- **A″. Framework types behind one front-end file,** which extracts route types from `typeof app`.
- **B. Shared endpoint contract.** `packages/shared/src/api/<domain>.ts` declares each endpoint as an object with zod schemas. The back end binds handlers to it; the framework validates and documents with the same schemas; the front end, tests and mocks type and parse from the same object.

### 6.2 Why B

1. **The front end needs the schemas at runtime anyway** (response parsing, about 100 form imports, the mocks). In A and A″ the framework's inferred types are a second source of the same facts.
2. **Type-check cost and fragility.** A and A″ load the back end's type graph into the front end's `tsc`; the two apps map `@/*` differently; A″ depends on framework type internals that changed between 1.4 and 2.
3. **Error typing.** Eden 2 types only 422 (V14). B types per-endpoint `errors`.
4. **Typed mocks and typed back-end tests** from the same object.
5. **Isolation (P3).** Module route files and front-end calls do not mention the framework.

### 6.3 The entry

**As built (Phase 1b):** `packages/shared/src/api/endpoint.ts`, `api/permissions.ts`, `apps/back-end/lib/http/binding.ts`. Differences from the sketch below:

- `status` is required (200 or 201). `params` is required exactly when the path has `:name` segments, keyed by those names, and refused otherwise. `bodyKind` is normalised by `endpoint()`. `errors` entries are `{ codes?, codesWithIds? }`: the permission conflicts carry no code; `codesWithIds` (2026-10-15) names the media codes whose refusal at that status carries ids in `data`, never repeated in `codes`. The policy also carries `checksPassword`, which decides a 429.
- Options the policy decides: `permission` exactly on `auth: 'permission'`; `rateLimit: { scope, limit, window?, failClosed?, by }` exactly on `rateLimited` (`by: 'user'` refused on a public route); `maxJsonBodyBytes` only on a JSON body. `bind()` checks the same at boot.
- Other options: `failure` (the 500 message of an unexpected throw, as the legacy handler answered), `mapError` (the handler's throws only; admission's refusals never reach it, auth slice), `refusals` per part (D25; `bind()` refuses one for a part the entry does not validate), `preAuthIpLimit: false`, `credential` (2026-10-14, #5: the route's own credential read from the request head in admission, after the per-IP limit and before the session, answered as the handler's typed result; only the health probe uses it; kept general by the owner, §1.5), `timingFloor` (the handler then gets `meta.startFloor`), `timeoutSeconds`, `enabled`, `detail`, and the transitional `manifestQuery` (the legacy document's query prose, until Phase 2).
- The handler gets `{ params, query, body, actor, meta }` (output types; `actor` typed by the policy) and returns `{ message, data, meta?, headers?, cookies? }`: `data` is the response schema's input, `meta` is required on a list and refused elsewhere. No `status`: the declared one is the only success. `tests/unit/contract-types.test.ts` holds nine such refusals.

```ts
export const updatePermission = endpoint({
  method: 'PUT',
  path: '/api/dash/permissions/:id',
  params: z.object({ id: entityIdSchema }),
  body: adminUpdatePermissionBodySchema, // body kind: 'json' (default) | 'multipart' | 'none'
  status: 200, // the success status (F5)
  response: updatedAtSchema, // the success `data`; or { data, meta }; or { raw: schema } (health, /openapi.json)
  errors: { 409: { codes: [PERMISSION_NAME_TAKEN] } },
  policy: {
    auth: 'permission',
    captcha: false,
    reauth: false,
    rateLimited: true,
  }, // decides refusals
});
// back end:  bind(updatePermission, { permission: …, rateLimit: …, handler })
// Phase 4:   front end  await api(updatePermission, { params: { id }, body })
//            mocks      mock(updatePermission, resolver)
```

- **Policy flags** are in shared because the client must type the refusals they imply. **Server-only values** (limits, scopes, permission names if not public) stay in the binding, or in the back end's `lib` (the media tunables, §1.4); a docs sentence names one as `{{name}}` (D19). `bind()` asserts the two agree. The dashboard grant policy and the `:id` params schema are declared once, `GRANTED` and `idParams` in `api/common.ts` (2026-10-14, #16).
- **Input and output sides:** the client sends the request schema's `z.input`; the handler receives `z.output`. The handler returns the response schema's `z.input`; the client receives `z.output` (D7).
- **Client error types** also admit transport failures: offline, proxy pages, 5xx.
- **Raw mode** serves `GET /api/health/storage` and `/openapi.json`. As built (health + openapi slice): `response: { raw, refusals? }`, where `refusals` declares the raw bodies the handler answers at refusal statuses (the probe's `{ status: 'unauthorized' }` at 401, its degraded/error union at 503); the handler returns `{ raw, status }` typed per declared status (the probe's 401 comes from its `credential` since 2026-10-14, typed the same way), and each is validated like the success. A raw entry has no `RESPONSE_DATA` key (D29 holds envelopes).

## 9. Design points

### 9.1 Bindings

A binding = a contract entry + server options + a handler. `bind()` types the handler from the entry.

**Server options:** permission name and scope, rate-limit keys and limits, captcha, re-auth window, timing floor (`startFloor` + deadline, F20), refusal override (D25), JSON ceiling.

**Generic admission only (D22).** `admit()` handles origin, IP limit, session, **one static permission**, rate limit and captcha. These five routes keep contextual checks in core, called from the handler (F7):

| Route                                     | Why it is contextual                                                                                                                                                             | Gate                                                                                       |
| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `PUT /api/dash/users/:id`                 | the re-authentication window depends on the change (`editUserAsAdmin`); the caller's own id is refused (2026-10-10; was self-rename with a body chosen by `userId === targetId`) | permission; gate refuses own id (`notSelf`), handler asks the window (`handlerAsksReauth`) |
| `POST /api/upload/file`                   | permission from `?resource`; `purpose` resolved only after the check (no enumeration)                                                                                            | session; handler decides                                                                   |
| `POST /api/dash/users/me/change-password` | re-auth window required only when `currentPassword` is absent                                                                                                                    | session; handler decides                                                                   |
| `POST /api/dash/auth/reauth`              | attempt limiter after the session check and before the body; malformed body → 401                                                                                                | session + override                                                                         |
| `GET /openapi.json`                       | any dashboard view grant (`requireDashboardAccess`)                                                                                                                              | session; handler decides                                                                   |

**Phase 2 (users), as built:** the table missed three self-contextual routes. `GET /api/dash/users/:id` and `GET`/`DELETE /api/dash/users/:id/sessions` also admit the caller as its own target without a grant (each called `requirePermission` with `throwError: false`). All four `/users/:id` routes now declare `permission.orSelf: 'id'`: the gate resolves the grant without refusing, runs the limiter, then refuses a well-formed id other than the caller's with 403; a malformed id is left to params validation (422, today's order). Re-authentication on those bindings is the handler's (`gateAsksReauth`). Kept in the handler: the self/admin body choice of `PUT /:id` (gone 2026-10-10: `PUT /:id` now declares `notSelf: 'id'` instead of `orSelf`), `editUserAsAdmin`'s conditional window, change-password's conditional window. The gate does it because a handler check would read and validate the `DELETE …/sessions` body before its 403 (today: 403, body unread).

- **`PUT /api/dash/users/me`** (new, Phase 2): self-rename with the self schema, natively validated. Admitted with `permission.orSelf: true` (owner decision 2026-10-10), so a caller whose role is missing or inactive is refused 403. Since 2026-10-10 the only self-rename.
- **`PUT /api/dash/users/:id`**: self-rename removed on 2026-10-10 (owner, ahead of Phase 4). The administrative body alone, validated natively; `permission: { users, edit, notSelf: 'id', handlerAsksReauth: true }`. The gate refuses a well-formed id equal to the caller's with 403 `MSG_INSUFFICIENT_PERMISSIONS` right after the grant check, before the limiter and the body; the handler asks the window only for a sensitive change. The handler-validated body option is gone.
- **The upload query schema** publishes the syntax of `purpose` (`.meta()` only) and checks none of it: the handler resolves it after the permission check, as today, so a caller without the grant gets 403 whatever it names (corrected in the media slice: a runtime syntax check would have answered such a caller 400 before its 403, a change §12 did not list).

**Success status (F5).** The entry declares it; `bind()` types the handler's status to it; S4 registers the success schema under it. A test asserts no binding answers an undeclared success status. Six handlers answer 201 today.

### 9.2 Registration (S4) and hook order (F10)

For each binding, S4 registers through `.route(...)`:

- the parser: the gate's `parse` hook on every body binding (A test asserts every body binding has it);
- `params`, `query`, `body` as **compiled** schemas (D10);
- `response`: the success schema (D18 envelope) under the success status, plus every refusal the policy implies, plus the entry's `errors`, each with the core envelope its status needs (`refusalEnvelopeOf`, 2026-10-14, #6): `data: null`, or media ids where the entry names a code in that status's `codesWithIds` (2026-10-15; was any id-bearing code, `MEDIA_CODES_WITH_IDS`); each compiled once;
- the macro options, the refusal override, and `detail` (summary, description, tags, `security`).

**Refusals derived from policy (F31):** 401 (session), 401 `REAUTH_REQUIRED` (re-auth), 403 (permission; cross-origin write on every non-safe method, public routes included; failed captcha), 413 and 400 (body; 413 on a bodyless binding too, the request hook's declared-length check, 2026-10-14, #2), 400 "violates a business rule" where `errors[400]` is declared, 422 (input, unless overridden), 429 (rate limit; locked account on password routes) with `Retry-After`, 503 (database contention) with `Retry-After`, 500 everywhere. Also the `x-captcha-response` header param and `Set-Cookie` on session-cookie routes.

**Hook order is an invariant.** S1 registers every hook and the gate plugin before the first binding, then the bindings (and, until Phase 3, the legacy rows, D28), each GET with its HEAD route. A boot assertion checks that every registered route has the mapped error hooks and `afterResponse`; a sweep test over every binding checks the answer and log line for one refusal each.

Feature-flagged and dev-only rows are not registered, so they are neither served nor documented.

### 9.3 Order and the gate (D3)

| Step                                                                                                                                                                              | Where                                                                                         |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| URL/host guard, coarse `Content-Length` check, OPTIONS                                                                                                                            | `request` hook (S2)                                                                           |
| CORS                                                                                                                                                                              | plugin                                                                                        |
| **Gate** (`admit.ts` `runGate`): origin → pre-auth IP limit → the route's own credential (2026-10-14) → session → permission (`notSelf`) → rate limit → `orSelf` target → captcha | macro `parse` (non-GET JSON body bindings) or `transform` (all others); runs once per request |
| Body read: counted, binding ceiling, `application/json` only                                                                                                                      | the same `parse` hook, after the gate                                                         |
| Validation: headers → body → params → query (A6)                                                                                                                                  | native, compiled                                                                              |
| A key the query declares, named twice (D24)                                                                                                                                       | `runBinding`, first, after validation                                                         |
| `actor`                                                                                                                                                                           | `runBinding` reads it (`actorOf`); refuses when the gate did not run                          |
| Handler                                                                                                                                                                           | `runBinding`                                                                                  |
| Response validation, headers, cookies, log, queue                                                                                                                                 | `response` schemas, `mapResponse` (headers only), `afterResponse`                             |

- **Statuses stay 401 → 429 → 400/413 → 422,** as today. No body byte is read before the gate.
- **The hand-off.** `admit()` records the actor and a "gated" marker in a `WeakMap<Request, …>`. `transform` calls the gate again, which returns at once when marked. `runBinding` reads the map (`actorOf`) and throws when the marker is missing, on **every** binding including public ones, so a skipped gate cannot skip a rate limit or captcha (fail closed). The map is per request and lets go with the request (A2). Until 2026-10-14 a macro `derive` also read it; nothing used the `actor` it produced (#15).
- **Errors thrown in `parse`** arrive as `ParseError`; S6 unwraps `.cause`. One with no cause is Elysia's own parser failing, answered as an unreadable body (`UnreadableBody`, so `refusals.unreadableBody` applies; 2026-10-14).
- **Validation order (F19)** is fixed by Elysia. On routes that checked the id before the body, a request with both a malformed id and an invalid body may now get the body refusal first. Listed in §12.

### 9.4 Body reading (D4, D23) and multipart

- **JSON bindings.** The gate's `parse` hook calls the existing bounded reader (`boundRequestBody` / `readBoundedText` in `lib/http/request.ts`), extended to take the binding's ceiling. Over the ceiling → 413, and reading stops (chunked bodies included). Then `JSON.parse`, then the plain-object check of `requireJsonBody` (400 for arrays and scalars, as today).
- **Media type (D23).** Anything but `application/json` → **400 `MSG_INVALID_INPUT`**, today's answer. 415 was considered: more precise, but it changes a live contract for no client, and D18 freezes the wire. Re-decide with D5 in Phase 4 if wanted. The refusal still restores the CSRF layer `app.ts` counts on ("a JSON route needs a preflight").
- **Exact ceiling (F2).** The reader uses the matched binding's ceiling. S2's coarse check stays as the early refusal for declared lengths. This fixes `PUT /api/dash/media/files` inheriting the multipart ceiling of its `POST` sibling.
- **Bodyless bindings.** No body is read; a sent body is ignored, as today. Not verified: what the hook must return so Elysia's default parser does not run (Q1). A behaviour case (§9.10) asserts no byte is read.
- **Multipart (2 routes).** The body kind is `multipart`. The gate runs in `transform`, and the lazy form reader runs after it, as today. The contract's form schema is for types and the document only. Q1 decides between `parse: 'none'` and the hook.

### 9.5 Query (D24, F18)

- **One core check** rejects duplicate keys from the raw URL before validation (422), **on bindings that declare a query schema only**. Today only the data table does this; other routes take the first value. Listed in §12 as a deliberate change: Elysia would otherwise keep the last value silently. **Narrowed in Phase 2 (auth, owner-delegated):** a binding that declares no query reads none, so it keeps ignoring the query entirely, a repeated key included, and the document publishes no duplicate-key 422 there. A smaller contract change, and no meaningless 422 on routes such as `GET /api/dash/media/files/{id}` (`openapi-access.test.ts` asserts none is published). **Narrowed again 2026-10-14 (#5):** the check left the gate. It refuses only a key the query schema declares, and runs first in `runBinding`, after validation: a malformed id's 404 (`DELETE /api/dash/media/folders/not-an-id?recursive=true&recursive=true`) and the health probe's token keep their precedence, and an undeclared key named twice is ignored by the probe's non-strict query or refused as unknown by a strict one. `bind()` refuses a query schema that is not an object.
- **Query schemas are strict objects.**
- **Numeric parameters** use a digits-only string schema, not `z.coerce.number()`.
- **The schemas parse `sort` and `filters`** (JSON strings) and keep today's 422s for unknown keys. **Re-decided in Phase 2 (users): not in this rewrite.** The list query schema checks keys, digits and lengths; `parseDataTableParams` keeps deciding what `sort` and `filters` mean. Parsing them in the schema needs either a `.transform()` in a request schema (its handling by the document generator and by `z.compile` is unverified, and the handler type would differ from the wire) or a refinement that parses the JSON and the handler parsing it again; the column map makes the schema per route; and every refusal reads `MSG_INVALID_FILTER` either way (the query override), so a client sees no difference. Revisit in Phase 4, when the front end, which shares `parseSearchParams`, adopts the contract.

### 9.6 Error bodies (D18, D5, D25)

**Phase 1b:** an override is declared per input part (`refusals: { params?, query?, body? }`). One per binding would have answered a media body's 422 with the malformed-id 404. The duplicate-key refusal (D24) is the query part's, so the data-table list answers it with `MSG_INVALID_FILTER`, as `parseDataTableParams` did.

- **One core function builds every error body,** `errorBody(status, message, code?, data?)`. Until Phase 4 it returns today's envelope `{ success: false, message, code?, data }` with `application/json`. In Phase 4 it returns problem+json (`type: 'about:blank'`, `title`, `status`, `detail`, `code`, `data`, plus `message` on `/api/auth/*`). A unit test parses every declared refusal against the error schema (F6).
- **S6 maps every Elysia error class** (validation, parse, not found, unknown) and typed core errors, plus a fallback for non-`Error` throws. Since 2026-10-14 an invalid cookie signature (`InvalidCookie`) reaches the fallback as a logged 500, not a 400: only signed cookies or Elysia serialising a cookie raise it, and nothing configures either, so it is a server fault. It never returns Elysia's `problem()`, which forces Elysia's slug `type` (F23). Every mapped error passes `mapResponse` (A6), so headers and cookies apply (F9).
- **Request validation → 422** with the first issue's message. A new **issues overload of `zodIssueMessage`** in `packages/shared/src/validation/rules.ts` takes `ValidationError.errors` (F22). Never echo `found`.
- **Refusal override (D25).** The binding declares `{ status, message }`; S5 records it per request; S6 reads it. The document follows it.

| Answer today                       | Operations                                                                                                                                                                                     |
| ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| a fixed message (hides the branch) | `POST /api/auth/otp/send`, `/otp/verify`, `/forgot-password/send`, `/forgot-password/reset`, `/forgot-password/complete`, `/forgot-password/second-factor/send`, `/passwordless/send`          |
| 401 with the credentials message   | `POST /api/dash/auth/reauth`                                                                                                                                                                   |
| 404 for a malformed id             | `GET`/`PUT /api/dash/media/files/:id`, `POST …/files/:id/publish`, `POST …/files/:id/unpublish`, `GET`/`PUT`/`DELETE /api/dash/media/folders/:id`, `POST /api/dash/users/:id/two-factor/reset` |

- **Per-endpoint `errors`** replace the status tables; the media envelope is chosen per status from them (`refusalEnvelopeOf`, §9.2). A development check in `run()` asserts a thrown code is declared. **Enabled** (health + openapi slice, owner-delegated) outside production: every binding refusal's `code` must be in `declaredCodes(entry, status)`, the entry's `errors` at that status plus the codes its policy implies (`REAUTH_REQUIRED` at 401 on `reauth: true`); anything else is logged `binding.code.undeclared` and answered 500. `errors` may name any refusal status, 401, 429 and 503 included. **Revised 2026-10-14 (#2):** `declared()` (`lib/http/run.ts`) checks the status too (one `refusalsOf` does not list is a mismatch) and a business 400 (a 400 from the handler, the gate or `mapError` needs `errors[400]`; the input's own 400 passes), and runs under `responseCheckMode()`, as the success check does: off in production, logged `response.contract.mismatch` in development with the answer unchanged, recorded and answered 500 under the runner. It had enforced in development, so the development server answered 500 where production answered the real refusal, and the runner recorded nothing. **Revised 2026-10-15 (Q13):** `declaredCodes` returns `codes` and `codesWithIds` alike, and `refusalProblem` (`lib/http/run.ts`) also refuses ids without a code, ids under a code the status does not list in `codesWithIds`, and a listed code answered without ids, unless the code may name none (`idsAreOptional`: `FILE_IN_USE`, whose referrer can be gone or unregistered).

### 9.7 Responses (D7, D8)

- **`run()` returns the plain body,** never a `Response`, so validation and stripping apply (V4).
- **One core function builds every success body,** `successBody(message, data, meta?)`: today `{ success: true, … }`, in Phase 4 `{ message, data, meta? }`. Raw mode bypasses it.
- **One exit step on every response (F8).** `mapResponse` only writes headers: queued cookies (once: `finish` for a native `Response`, `answerValue` for a value answer; `withQueuedCookies` went 2026-10-14), the response policy, security headers. It mutates a native `Response`'s headers (Better Auth's), which beats `set.headers` (A6). `afterResponse` writes the access log with the final status and drains the queue. Several `Set-Cookie` values go through `set.headers` (A5).
- **Response validation in production (D8).** A failure is a 500 with the error body and an operator log naming **paths and issue codes only**: `ValidationError.value` holds the whole body. Since 2026-10-14 (#7) the 500 carries none of the refused answer's headers or cookies (`withdrawValue` restores the header bag), so a success header such as a future `Cache-Control` cannot reach the error; the queued session cookies return to the queue and go out with it.
- **`contractIssues` outside production (F13).** S7 also runs the `.meta()` read-back check in development and tests, so the UUID, `date-time`, `uniqueItems`, `minimum` and `const` guarantees stay checked (A12). They stay out of zod so deployed clients do not refuse values that change between deploys.
- **Interim (D18):** a response failing its schema becomes a logged 500. That happens only on a server bug. **Phase 4 (F14):** a dedicated code in `@app/shared/error-codes` that the client maps to `committedError()`, so a committed write is never retried; validate before commit where practical.

### 9.8 HEAD, abort, and 1.4 leftovers

- **HEAD (F15).** Every GET is registered for HEAD too, with the GET's own options and handler, so validation and refusals are the GET's. **`z.compile` consequences (D10).**

1. **Back end only.** `packages/shared` never calls it; S4 compiles.
2. **Identity.** A compiled schema is a clone. `.meta()` is kept (V23). Anything keyed by identity (D19's registry, D29's identity test) uses the original or a child instance the clone shares.
3. **Boot:** about 50 ms for the contract schemas; eager compilation fails the boot, not a request.
4. **Same results:** success, output and issues are identical (A11, 178,500 inputs). **Not** the same callbacks: a refinement runs twice on invalid input (F21), hence D21.
5. **Hostile input** gains nothing (Z6); the gate, ceilings and IP limit bound it.
6. **Server code generation** (`new Function`) is fine on Bun.
7. **Handler-internal parses** (e.g. `PUT /api/dash/users/:id` until Phase 4) stay plain. That is the cost of rejecting the global mode.
